# Module 3 class notes: CPU scheduling

## CPU scheduling and the CPU–I/O burst cycle (slides 2–4)
CPU scheduling is the basis of a multiprogrammed OS: by switching the CPU among processes the OS makes the computer more productive. The objective of multiprogramming is to have some process running all the time, to maximise CPU utilisation. A process runs until it must wait, typically for an I/O request to complete; several processes are kept in memory (ready queue, waiting queue), and when one has to wait the OS takes the CPU away and gives it to another. Process execution is a cycle of CPU execution and I/O wait: processes alternate between a CPU burst and an I/O burst, ending with a final CPU burst.

## CPU scheduler, dispatcher and types of schedulers (slides 5–8)
Whenever the CPU becomes idle, the short-term scheduler (CPU scheduler) selects one of the processes in the ready queue. The dispatcher is the module that gives control of the CPU to the selected process: it does the context switch, switches to user mode and jumps to the right instruction. The time the dispatcher takes to stop one process and start another is the dispatch latency. Scheduler = selects the process; dispatcher = dispatches it to the CPU and should be fast.
Types of schedulers: long-term scheduler (selects processes from secondary storage and loads them into memory; runs rarely), medium-term scheduler (suspends and resumes processes to manage memory; occasionally), short-term scheduler / CPU scheduler (selects the next ready process; very frequently, milliseconds).
Why scheduling is needed: there is usually one CPU core (or a few), several processes cannot run on the same core at once, so the OS must decide which process gets the CPU next. Goals: maximise CPU utilisation, improve throughput, reduce waiting time, improve response time, ensure fairness.
Process scheduling vs CPU scheduling: process scheduling is the overall management of process execution (admission, suspension, termination; long-, medium- and short-term schedulers; the whole life cycle). CPU scheduling decides only which ready process gets the CPU (short-term scheduler; mostly about the running state).

## When scheduling decisions happen; preemptive vs non-preemptive (slides 9–15)
CPU scheduling decisions may take place when a process (1) switches from running to waiting (e.g. an I/O request), (2) switches from running to ready (e.g. an interrupt), (3) switches from waiting to ready (e.g. I/O completes), (4) terminates. For 1 and 4 there is no choice: a new process must be selected. For 2 and 3 there is a choice.
The scheduler runs whenever a process is created, terminates, requests I/O and blocks, an I/O completes, or a timer interrupt occurs (preemptive scheduling). How it works: processes waiting for the CPU sit in the ready queue; the scheduler picks one using an algorithm; the dispatcher assigns it to the CPU; the process then completes, requests I/O (moves to waiting), or is preempted back to the ready queue.
Non-preemptive (cooperative) scheduling: decisions only in cases 1 and 4; the running process keeps the CPU until it finishes or blocks; simpler; suits batch systems; example FCFS. Preemptive scheduling: the CPU can be taken away from a running process; better responsiveness; suits interactive systems; example Round Robin. Virtually all modern operating systems (Windows, macOS, Linux, UNIX) use preemptive scheduling.
CPU burst time is time executing instructions on the CPU (process state running); I/O burst time is time waiting for an I/O device (process state waiting/blocked), during which the CPU is free to run another process.

## Scheduling criteria and formulas (slides 16–19)
CPU utilisation = CPU busy time / total time × 100 (maximise). Throughput = number of completed processes / total time (maximise). Turnaround time TAT = completion time − arrival time (minimise). Waiting time WT = time spent waiting in the ready queue = TAT − CPU burst time (minimise). Response time RT = time of first CPU allocation − arrival time (minimise). Context switches: the number of times the CPU switches between processes; pure overhead (minimise). Fairness: each process gets an equitable share (maximise).
The notes also state: TAT = waiting time + CPU burst time + I/O burst time (or TAT = WT + CPU burst when there is no I/O). In non-preemptive scheduling response time = waiting time, because a process starts only once. In preemptive scheduling response time ≤ waiting time.

## How the notes compute CPU utilisation, throughput and context switches
Every worked example ends with the same performance summary. Total system time is measured from 0 to the last completion time (e.g. 25 ms in the FCFS-with-I/O example even though the first process arrives at 2). CPU utilisation = total CPU burst time / total system time × 100 (e.g. 21/25 = 84%). Throughput = number of processes / total system time (e.g. 5/25 = 0.2 processes/ms). Number of context switches = how many times the Gantt chart changes from one process to a different process; an idle gap is not counted when the same process resumes (P5 → idle → P5 is no switch) and the first dispatch is not counted. Without preemption FCFS gives N − 1 switches for N single-burst processes.

## Comparison of non-preemptive algorithms (slide 21)
FCFS: runs the process that arrived first until completion; selection by arrival time; no burst time needed; no starvation; high convoy effect; usually high waiting time; very simple; fair by arrival order but poor response time; suits simple batch processing. SJF (non-preemptive): among available processes picks the smallest CPU burst and runs it to completion; needs burst times; long processes may starve; very low convoy effect; minimum average waiting time among non-preemptive algorithms; needs burst prediction. Priority (non-preemptive): picks the highest priority (usually the lowest priority number); low-priority processes may starve; suits critical tasks. In all three a newly arrived process waits until the current one finishes.

## Comparison of preemptive algorithms (slide 22)
SRTF: always runs the process with the shortest remaining burst; a newly arrived process with a shorter remaining time preempts immediately; minimum average waiting and turnaround time; frequent context switches; long processes may starve. Preemptive priority: runs the highest-priority process; a newly arrived higher-priority process preempts immediately; low-priority processes may starve. Round Robin: each process gets a fixed time quantum, then is preempted and moved to the end of the ready queue; no starvation; fair sharing; performance depends on the quantum; many context switches; a new process joins the ready queue and waits its turn. MLFQ: several queues with different priorities and quanta; the highest-priority queue is served first; processes move between queues based on CPU usage; very low starvation (aging and promotion); hard to implement and tune; used in modern general-purpose OSs.

## FCFS – First Come First Serve (slide 23)
The simplest algorithm: the process that requests the CPU first is allocated it first, implemented with a FIFO queue. New processes (their PCBs) are added at the tail; when the CPU is free it goes to the process at the head, which is removed from the queue. FCFS is non-preemptive. Its average waiting time is often high and it is not suitable for time-sharing systems (convoy effect: short processes wait behind a long one).

## SJF – Shortest Job First (slides 39–43)
SJF associates with each process the length of its next CPU burst; when the CPU is available it goes to the process with the smallest next CPU burst. If two processes have the same next burst, FCFS breaks the tie. SJF can be non-preemptive (SJN) or preemptive (SRTF). A better name is shortest-next-CPU-burst. SJF is optimal (minimum average waiting time) but the real difficulty is knowing the length of the next CPU request, so it cannot be implemented exactly at the short-term level; it is approximated by predicting the next burst from previous ones.
Example 1 (non-preemptive, all at 0): P1 6, P2 8, P3 7, P4 3. Gantt P4 0–3, P1 3–9, P3 9–16, P2 16–24. WT P1 3, P2 16, P3 9, P4 0; average 7 ms (FCFS would give 10.25 ms).

## Priority scheduling (slides 57–58)
A priority is associated with each process and the CPU goes to the highest-priority process; equal priorities are served FCFS. SJF is a priority algorithm where priority is the inverse of the predicted next CPU burst. Priority scheduling can be preemptive (a newly arrived process with higher priority than the running one preempts it) or non-preemptive (the new process is simply put at the head of the ready queue). The notes show both conventions, smallest integer = highest priority and largest integer = highest priority; the worked examples use smallest integer = highest priority unless the question says otherwise. Problem: starvation of low-priority processes. Solution: aging, increasing the priority of a process as time passes.

## Round Robin (slides 72–74)
Round Robin is designed for time-sharing systems: like FCFS but with preemption. A time quantum (time slice), generally 10–100 ms, is the maximum CPU time a process gets in one turn before it is preempted. The ready queue is a circular FIFO queue: new processes are added to the tail; the scheduler picks the first process, sets a timer to interrupt after one quantum and dispatches it. If the quantum is larger than every burst, RR behaves like FCFS (non-preemptive in effect); if the quantum is smaller than the bursts it causes many context switches, which overloads the OS. Flow: select a process; if its remaining burst < quantum it executes to completion; otherwise it executes for one quantum, and if not finished it goes back to the tail of the ready queue.
Ready-queue order used in the worked examples: when a process arrives at the same moment a time slice ends, the newly arrived process is put in the queue before the preempted process (Example 2 and the RR-with-I/O example both do this).

## Multilevel queue scheduling – MLQ (slides 148–154)
MLQ divides the ready queue into several queues arranged in a hierarchy, e.g. system processes, interactive processes and batch processes. Each queue has its own priority level and its own scheduling algorithm (e.g. queue 1 and 2 Round Robin, queue 3 FCFS). A process is assigned permanently to one queue, based on priority, resources or process type. Scheduling among the queues: (1) fixed-priority preemptive scheduling, where each queue has absolute priority over lower queues (no batch process runs unless queues 1 and 2 are empty, and a running batch process is preempted when a system or interactive process arrives); or (2) time slicing, where each queue gets a share of CPU time (e.g. 50%, 30%, 20%).
Example: P1 in Queue 1 (RR, q = 2, AT 0, BT 5), P2 in Queue 2 (FCFS, AT 1, BT 4), P3 in Queue 3 (SJF, AT 2, BT 3). Queue 1 is served first: P1 0–2, 2–4, 4–5; then P2 5–9 (FCFS, runs fully); then P3 9–12.
Advantages: organised separation of process types, predictable, good response for interactive/system processes, ensures critical processes are not delayed. Disadvantages: starvation of low queues, processes cannot move between queues (inflexible), more bookkeeping, some queues may dominate the CPU.

## Multilevel feedback queue scheduling – MLFQ (slides 155–158)
MLFQ is like MLQ but processes can move between queues based on their CPU usage or I/O behaviour; priorities change dynamically. CPU-heavy processes move down; I/O-bound or short processes stay up (and can move up). Each queue has its own time slice; higher queues have shorter slices; a process that uses its whole slice may be demoted. Preemption is allowed: a higher-priority queue interrupts a lower one.
Classic setup: Q0 RR with quantum 8 ms, Q1 RR with quantum 16 ms, Q2 FCFS. A new process enters Q0 and gets 8 ms; if it does not finish it moves to Q1 and gets 16 more ms; if it still does not finish it is preempted and moved to Q2. If a process completes, or gives up the CPU for I/O, within its 8 ms its priority does not change and when it comes back to the ready queue it starts again in Q0.
Question: a CPU-bound process needs 40 s; the quantum is 2 s at the first level and increases by 5 s per level (2, 7, 12, 17, 22). It runs 2 + 7 + 12 + 17 = 38 s in the first four queues, then 2 s in queue 5: it is interrupted 4 times and completes in queue 5.

## Multiprocessor scheduling – concepts (slides 182–187, 201)
With more than one CPU, scheduling must decide which CPU handles which task and balance the load. With identical (homogeneous) processors any processor can run any process. Processor affinity: a process prefers the processor it last ran on, because its data is in that cache; soft affinity (the OS tries but does not guarantee) vs hard affinity (restricted to a set of CPUs, e.g. sched_setaffinity() in Linux). Load balancing avoids overloaded and idle processors: push migration (a busy processor pushes tasks to less busy ones) and pull migration (an idle processor pulls tasks). Multicore processors: memory stall (waiting for data not in cache, up to 50% of the time) is hidden by hardware multithreading, coarse-grained (switch thread on a long-latency event) or fine-grained (switch every cycle). Virtualisation can distort time slices of guest OSs.
Approaches: asymmetric multiprocessing (AMP), a master–slave approach where one master processor makes the scheduling decisions and does I/O while the others run only user code (simple; if a slave fails the rest keeps working, but the master is a bottleneck and a single point of failure); symmetric multiprocessing (SMP), where each processor schedules itself, with either a common ready queue or private per-CPU ready queues. Pros: high throughput, better resource use, scalability. Cons: complex, load balancing is hard, migration and affinity overhead, virtualisation may affect real-time guarantees.
