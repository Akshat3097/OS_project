# Processes, context switches and the extra scheduling slides

## Process concept (Module 2, slides 37–39)
A process is a program in execution; its execution progresses sequentially. Its parts: the program code (text section); the current activity (program counter, processor registers); the stack (temporary data: function parameters, return addresses, local variables); the data section (global variables); the heap (memory allocated at run time). A program is a passive entity stored on disk (an executable file); a process is active, lives in memory and executes instructions. A program becomes a process when the executable is loaded into memory, and one program can become several processes.

## Process states and the PCB (Module 2, slides 40–41)
States: new (being created), ready (waiting to be assigned to a processor), running (instructions are being executed), waiting (waiting for some event such as I/O completion), terminated (finished). The OSTEP-style slides name them running, ready, blocked (waiting for an event, e.g. a disk read; unblocked by the disk interrupt), new and dead. The Process Control Block (PCB, also called task control block) holds each process's information: process state, program counter, CPU registers, CPU-scheduling information (priority, queue pointers), memory-management information, accounting information (CPU used, elapsed time, limits) and I/O status (devices allocated, open files). The OS keeps a list of all active PCBs.

## Scheduling queues and context switching (Module 2, slides 42–46)
The process scheduler selects among available processes for the next execution on a CPU core, aiming to maximise CPU use and switch processes quickly. It keeps scheduling queues: the ready queue (processes in main memory ready and waiting to execute) and wait queues (processes waiting for an event such as I/O); processes migrate among these queues. A context switch happens when the CPU switches from one process to another: the system saves the state (context) of the old process in its PCB and loads the saved state of the new one. Context-switch time is pure overhead because no useful work is done; it is longer for a more complex OS and PCB and depends on hardware support (some CPUs have several register sets so several contexts are loaded at once).

## How the OS runs a process and switches (Theory slides: process abstraction and execution mechanism)
The OS creates a process by allocating memory and building its memory image (code and data loaded from the executable, a stack and a heap), opening the standard files (stdin, stdout, stderr) and initialising the registers so the program counter points at the first instruction; then it gets out of the way and the process runs directly on the CPU. A process consists of a PID, its memory image, its CPU context (PC, registers, stack pointer) and its open file descriptors. The OS timeshares the CPU: the policy decides which process to run, the mechanism does the context switch.
System calls use a trap instruction: the CPU moves to kernel mode, switches to the kernel stack, saves the user context, and jumps to the handler found in the Interrupt Descriptor Table (IDT, set up at boot). Traps also happen on program faults and device interrupts. return-from-trap restores the context and returns to user mode. Before returning, the OS may switch to another process: when the process exited or was terminated, made a blocking call, or has run too long. Non-preemptive (cooperative) schedulers switch only when a process blocks or ends; preemptive ones rely on a periodic timer interrupt to take the CPU back. During a context switch from A to B the OS saves A's context on A's kernel stack, switches to B's kernel stack, restores B's context and returns from the trap into B's user code.

## Extra slides: scheduling introduction (OSTEP-based, session 7)
Simplifying workload assumptions that are relaxed one by one: every job runs for the same time, all arrive at once, all use only the CPU (no I/O), and the run time of each job is known. Turnaround time = completion time − arrival time; fairness is another metric, often at odds with performance. FIFO/FCFS is simple but suffers the convoy effect (A needs 100 s, B and C 10 s each: B and C wait behind A). SJF runs the shortest job first (non-preemptive) and fixes that case, but if A starts at 0 and B and C arrive at 10, they still wait. STCF (shortest time-to-completion first, also called preemptive SJF, PSJF; the same as SRTF) adds preemption: when a job arrives, run whichever job has the least time left. Response time = first time scheduled − arrival; STCF is poor for response time. Round Robin runs each job for a time slice (scheduling quantum, a multiple of the timer-interrupt period) and then switches: good response time but poor turnaround. Short slices give better response but context-switch cost dominates; long slices amortise switching but worsen response. With I/O: when a job issues I/O it blocks and the scheduler runs another job; when the I/O completes an interrupt moves it back to ready, so CPU and I/O overlap and utilisation improves.

## Extra slides: multi-level feedback queue (OSTEP-based, session 8)
MLFQ learns from the past to predict the future: it aims to optimise turnaround (run short jobs first) and minimise response time without knowing job lengths in advance. Rules: Rule 1: if Priority(A) > Priority(B), A runs. Rule 2: if Priority(A) = Priority(B), A and B run in Round Robin. Rule 3: a new job is placed at the highest priority. Rule 4a: if a job uses up an entire time slice its priority is reduced; Rule 4b: if it gives up the CPU before the slice ends it keeps its level (so MLFQ approximates SJF). Problems: starvation when there are many interactive jobs, gaming the scheduler (issue an I/O just before the slice ends), and jobs changing behaviour. Rule 5 (priority boost): after some period S move all jobs to the top queue. Better accounting replaces 4a/4b: once a job uses up its time allotment at a level, regardless of how many times it gave up the CPU, it moves down. Tuning: high-priority queues get short slices (e.g. 10 ms), low ones longer (e.g. 20 ms, 40 ms, or hundreds of ms); Solaris time-sharing uses 60 queues with slowly increasing slices from 20 ms and boosts about every second.

## Extra slides: proportional-share scheduling (OSTEP-based, session 9)
A fair-share scheduler guarantees each job a percentage of CPU time instead of optimising turnaround or response time. Tickets represent a share: A with 75 tickets and B with 25 should get 75% and 25%. Lottery scheduling draws a random winning ticket each time slice (A holds 0–74, B 75–99) and runs its owner; the longer the jobs compete, the closer they get to the desired shares, but for short jobs unfairness can be large. Ticket currency (users allocate tickets in their own currency, converted to global value), ticket transfer (hand tickets to another process temporarily) and ticket inflation (a process raises or lowers its own tickets). Implementation: walk the job list adding tickets until the running sum exceeds the random winner. Stride scheduling is deterministic: stride = a large number / tickets (10,000/100 = 100 for A, 10,000/50 = 200 for B); always run the process with the lowest pass value and then add its stride to its pass. A new job entering with pass 0 would monopolise the CPU.

## Extra slides: multiprocessor scheduling (OSTEP-based, session 10)
Adding CPUs does not make one single-threaded application faster; it must be rewritten with threads. Caches make memory look fast but bring cache coherence problems (CPU 1 may read a stale copy after CPU 0 updates a value); bus snooping lets caches invalidate or update copies. Shared data across CPUs still needs locks (e.g. a list pop must be protected by a mutex). Cache affinity: keep a process on the same CPU where its state is cached. Single-queue multiprocessor scheduling (SQMS) puts all jobs in one shared queue: simple, but needs locking (poor scalability) and jobs bounce between CPUs (poor affinity) unless the scheduler preserves affinity for most jobs and migrates only some. Multi-queue scheduling (MQMS) gives each CPU its own queue: scalable and good affinity, but load imbalance (a CPU may sit idle or one job may get twice the CPU of others), fixed by migration and work stealing (a queue low on jobs peeks at fuller queues and steals jobs; too much peeking costs overhead). Linux schedulers: the O(1) scheduler (priority-based, multiple queues, interactivity focus) and the Completely Fair Scheduler (deterministic proportional share).
