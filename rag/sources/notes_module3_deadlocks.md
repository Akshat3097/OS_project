# Module 3 class notes: deadlocks

## What a deadlock is (slides 202–204)
Deadlock is a state in which two or more processes are stuck forever because each is waiting for a resource held by another. Example: P1 holds R1 and needs R2 while P2 holds R2 and needs R1: who moves first? No one. It happens only when four conditions exist together: mutual exclusion, hold and wait, no preemption and circular wait. Deadlocks are handled by prevention, avoidance (Banker's algorithm) or detection and recovery.
System model: resource types R1 … Rm (CPU cycles, memory space, I/O devices), each with Wi instances. A process uses a resource in the order request → use → release. Deadlock arises when processes hold some resources while waiting for others.
Everyday and system examples of deadlock: printer and scanner (P1 holds the printer and waits for the scanner, P2 the opposite); database transactions locking rows A and B in opposite order; two mutex locks taken in opposite order by two threads; two programs locking files A and B in opposite order; four cars in a traffic intersection each waiting for the next; dining philosophers each holding one fork.

## The four necessary conditions (slide 205)
Deadlock can arise only if all four hold simultaneously. Mutual exclusion: only one process can use a resource at a time (non-sharable resources). Hold and wait: a process holds at least one resource while waiting to acquire others held by other processes. No preemption: a resource cannot be taken from a process; it is released only voluntarily. Circular wait: a set of processes wait for each other in a circle (P0 waits for P1, P1 for P2, …, Pn for P0).

## Resource-allocation graph and wait-for graph (slides 206–208)
A resource-allocation graph (RAG) shows who holds what and who waits for what. Process nodes are circles (P1, P2, …); resource nodes are squares or rectangles, with the number of instances shown inside (dots or a count, e.g. R1 (2)). A request edge Pi → Rj means Pi has requested Rj and is waiting; an assignment edge Rj → Pi means an instance of Rj is held by Pi. If the graph has no cycle there is no deadlock. If it has a cycle: with one instance per resource type there is a deadlock; with several instances per type there is only a possibility of deadlock.
The wait-for graph removes the resource nodes and draws only processes: an edge Pi → Pj means Pi waits for a resource held by Pj. It is most useful when each resource has a single instance: then a cycle in the wait-for graph means deadlock. With multiple instances a cycle is only a warning sign.

## Deadlock handling strategies (slides 209–210)
Ignore the problem (the ostrich approach): assume deadlocks are rare; most general-purpose OSs such as Windows and Linux do this because constant checking adds overhead. Prevention: make sure at least one of the four conditions can never hold, e.g. request all resources at once (no hold and wait), impose an order on resource requests by giving each resource (mutex) a unique number and acquiring in that order (no circular wait), allow resource preemption. Avoidance: examine the allocation state dynamically and grant a request only if the system stays in a safe state; the Banker's algorithm checks every request. Detection and recovery: let deadlocks happen, detect them (cycles in the graph or the detection algorithm), then recover by terminating processes, preempting resources and restarting, or rolling back to a safe point.

## Deadlock prevention (slide 211)
Prevention eliminates at least one necessary condition. (1) Eliminate hold and wait: allocate all resources a process needs before it starts; this lowers device utilisation. (2) Allow resource preemption: take resources from a process when a higher-priority process needs them. (3) Impose resource ordering: number every resource type and allow requests only in increasing order (R1 < R2 < R3), so no cycle can form. (4) Disallow mutual exclusion where possible by making resources sharable.

## Deadlock avoidance and safe state (slides 212–216)
Avoidance needs a priori information: each process declares the maximum number of instances of each resource type it may need. The avoidance algorithm examines the resource-allocation state (available, allocated, maximum demands) so that a circular wait can never happen. A system is in a safe state if there is a sequence <P1, P2, …, Pn> of all processes such that each Pi's remaining needs can be satisfied by the currently available resources plus the resources held by all Pj with j < i: if Pi's needs are not immediately available it waits until the earlier ones finish, then gets its resources, runs, releases them, and so on. Safe state → no deadlock; unsafe state → possibility of deadlock; avoidance ensures the system never enters an unsafe state.
For a single instance of each resource type the resource-allocation-graph algorithm is used; for multiple instances, the Banker's algorithm. In the RAG scheme a claim edge Pi → Rj (dashed) says Pi may request Rj; it becomes a request edge when the request is made and an assignment edge when granted, and back to a claim edge when released. A request is granted only if converting the request edge into an assignment edge does not create a cycle.

## Banker's algorithm data structures (slides 217–218)
For multiple instances of each resource type. Each process must claim its maximum use in advance; a requesting process may have to wait; a process that gets all its resources must return them in finite time. The algorithm has two parts: the safety algorithm and the resource-request algorithm. With n processes and m resource types: Available (vector of length m; Available[j] = k means k instances of Rj are free), Max (n × m; Max[i,j] = k means Pi may request at most k instances of Rj), Allocation (n × m; currently allocated), Need (n × m; Need[i,j] = Max[i,j] − Allocation[i,j], what Pi may still request).

## Banker's safety algorithm (slides 219, 231)
1. Work = Available; Finish[i] = false for every i. 2. Find an i with Finish[i] = false and Need_i ≤ Work; if none exists go to step 4. 3. Work = Work + Allocation_i; Finish[i] = true; go to step 2. 4. If Finish[i] is true for all i, the system is in a safe state.
Slide 231 version with flags: inputs are any 2 of the 3 matrices (Max, Need, Allocation) and any 1 of (Available, total number of instances). Step 1: flag[i] = 0 for all i; Need = Max − Allocation. Step 2: find Pi with flag[i] = 0 and Need_i ≤ Available. Step 3: if found, flag[i] = 1 and Available = Available + Allocation_i, go to step 2; else go to step 4. Step 4: if every flag is 1 the system is safe, otherwise unsafe. Total instances = Allocated + Available. In each step: compare Need with Available, then Available = Available + Allocated.

## Banker's resource-request algorithm (slides 220, 240)
For a request Request_i from Pi: 1. If Request_i ≤ Need_i go to step 2; otherwise raise an error, because the process has exceeded its maximum claim. 2. If Request_i ≤ Available go to step 3; otherwise Pi must wait, because the resources are not available. 3. Pretend to allocate: Available = Available − Request_i; Allocation_i = Allocation_i + Request_i; Need_i = Need_i − Request_i. Run the safety algorithm: if the new state is safe the resources are allocated to Pi; if unsafe Pi must wait and the old state is restored. The system does not allocate immediately; it pretends first and checks for a safe state.

## Banker's Example 1 (slides 221–230)
Resources A B C D. Allocation: P0 0 0 1 2, P1 1 0 0 0, P2 1 3 5 4, P3 0 6 3 2, P4 0 0 1 4. Max: P0 0 0 1 2, P1 1 7 5 0, P2 2 3 5 6, P3 0 6 5 2, P4 0 6 5 6. Available 1 5 2 0. Need = Max − Allocation: P0 0 0 0 0, P1 0 7 5 0, P2 1 0 0 2, P3 0 0 2 0, P4 0 6 4 2. Safe sequence <P0, P2, P3, P4, P1>: P0 finishes (Available 1 5 3 2), P1 cannot (needs 7 B), P2 can (2 8 8 6), P3 (2 14 11 8), P4 (2 14 12 12), then P1. Total instances = Allocated + Available = 3 14 12 12.

## Banker's Example 2 with requests (slides 232–257)
Allocation: P0 2 0 0 1, P1 3 1 2 1, P2 2 1 0 3, P3 1 3 1 2, P4 1 4 3 2. Max: P0 4 2 1 2, P1 5 2 5 2, P2 2 3 1 6, P3 1 4 2 4, P4 3 6 6 5. Available 3 3 2 1. Need: P0 2 2 1 1, P1 2 1 3 1, P2 0 2 1 3, P3 0 1 1 2, P4 2 2 3 3.
Safe: sequence <P0, P3, P1, P2, P4>; other valid safe sequences include <P0, P3, P4, P1, P2>, <P0, P3, P2, P1, P4>, <P0, P3, P2, P4, P1>.
Request from P1 for (1,1,0,0): (1,1,0,0) ≤ Need(P1) (2,1,3,1) and ≤ Available (3,3,2,1). Pretend: Need(P1) = (1,0,3,1), Available = (2,2,2,1), Allocation(P1) = (4,2,2,1). Safe sequence <P0, P3, P4, P1, P2>, so the request is granted immediately.
Request from P4 for (0,0,2,0): ≤ Need(P4) (2,2,3,3) and ≤ Available (3,3,2,1). Pretend: Allocation(P4) = (1,4,5,2), Need(P4) = (2,2,1,3), Available = (3,3,0,1). No process's Need fits, so there is no safe sequence: the request is NOT granted and the deadlock is avoided.

## Deadlock detection (slides 258–262)
Detection lets the system enter a deadlock and then finds it: for single-instance resources with a wait-for graph (look for a cycle), for multiple instances with a Banker's-style algorithm. Detection algorithm: 1. Work = Available; for each i, Finish[i] = false if Allocation_i ≠ 0, otherwise true. 2. Find i with Finish[i] = false and Request_i ≤ Work; if none, go to step 4. 3. Work = Work + Allocation_i; Finish[i] = true; go to step 2. 4. If Finish[i] = false for some i the system is deadlocked, and every such Pi is deadlocked. The algorithm needs O(m × n²) operations.
Example: five processes P0–P4, three resource types A (7 instances), B (2), C (6). Allocation: P0 0 1 0, P1 2 0 0, P2 3 0 3, P3 2 1 1, P4 0 0 2. Request: P0 0 0 0, P1 2 0 2, P2 0 0 0, P3 1 0 0, P4 0 0 2. Available 0 0 0. Sequence <P0, P2, P3, P1, P4> gives Finish[i] = true for all i: no deadlock. If P2 requests one more instance of C (Request P2 = 0 0 1), the sequence stops after P0: P1, P2, P3 and P4 are deadlocked.

## When to run detection, and recovery (slides 263–264)
How often to invoke detection depends on how often deadlock is likely and how many processes would need rolling back (one for each disjoint cycle). If it is invoked at arbitrary times there may be many cycles and it is impossible to tell which thread caused the deadlock. Recovery by process termination: abort all deadlocked processes, or abort one at a time until the cycle is gone, choosing by priority, how long it has computed and how long it still needs, resources used and needed, how many processes must be terminated, and whether it is interactive or batch. Recovery by resource preemption: select a victim (minimum cost), roll it back to a safe state and restart it, and avoid starvation (the same process always picked as victim) by counting rollbacks in the cost.

## Deadlock practice problem from the Theory folder (Deadlock problem.pdf)
Four processes P0–P3 and four resource types with several instances. R1 has two instances, one allocated to P0 and one to P1. R2 has three instances, one each allocated to P1, P2 and P3. R3: two instances allocated to P0 and one free. R4 has two instances, one allocated to P3 and one to P2. P1 requests one R1; P0 requests one R2; P3 requests one R1 and two R2; P0 and P2 each request one R3. (i) Draw the resource-allocation graph. (ii) Apply the Banker's (detection) algorithm to check for deadlock. (iii) If there is no deadlock, write the safe sequence.
Worked with the detection algorithm: Allocation (R1 R2 R3 R4) P0 1 0 2 0, P1 1 1 0 0, P2 0 1 0 1, P3 0 1 0 1; Request P0 0 1 1 0, P1 1 0 0 0, P2 0 0 1 0, P3 1 2 0 0; Available 0 0 1 0. ## Deadlocks in concurrent programs (Theory slides: Concurrency bugs)
Deadlock bug, classic form: Thread 1 holds lock L1 and waits for L2 while Thread 2 holds L2 and waits for L1. It occurs only if the executions overlap and a context switch happens after a thread has acquired just one lock. It appears as a cycle in the dependency graph, and all four conditions (mutual exclusion, hold-and-wait, no preemption, circular wait) must hold. Preventing circular wait: acquire locks in a fixed total (or partial) order, e.g. both threads take L1 before L2, or order locks by the address of the lock variable. Preventing hold-and-wait: acquire all locks at once, e.g. by first taking a master lock (reduces concurrency). Avoidance: if the OS knew which locks each process needs it could schedule them so deadlock cannot occur (the Banker's algorithm is popular but assumes knowledge rarely available in real life). Detect and recover: reboot or kill deadlocked processes.
