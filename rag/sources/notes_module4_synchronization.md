# Module 4 class notes: concurrency and process synchronization

## Independent and cooperating processes (slides 2–3)
Processes executing concurrently are either independent (cannot affect or be affected by other processes) or cooperating (can affect or be affected by others). Any process that shares data with other processes is a cooperating process. Reasons to cooperate: information sharing, computation speed-up, modularity, convenience. Example: in a bank ATM one process reads the card and PIN, another checks the account balance and a third dispenses cash; they must communicate and coordinate. Cooperating processes need an inter-process communication (IPC) mechanism.

## Inter-process communication: shared memory and message passing (slides 4–15)
Two fundamental IPC models. Shared memory: the cooperating processes establish a shared region (normally in the address space of the creating process; others attach it); process A writes, process B reads directly. Fast, but needs synchronization such as semaphores; like several people editing one shared Google Doc. Message passing: processes exchange messages through the kernel with send(message) and receive(message) system calls, without sharing an address space (sockets, message queues, pipes); simpler and safer but slower because the kernel is involved; useful in distributed systems; like a group chat where every message goes through the server.
Message passing details: P and Q must establish a communication link and exchange messages. Direct communication names the other process explicitly (send(P, message), receive(Q, message)); the link is set up automatically, belongs to exactly one pair, one link per pair, usually bi-directional. Indirect communication goes through mailboxes (ports) with unique ids (send(A, message), receive(A, message)); a link exists only if processes share a mailbox, may connect many processes, and a pair may share several links. If P1, P2 and P3 share mailbox A and P1 sends, who receives? Solutions: allow a link between at most two processes, allow only one receive at a time, or let the system pick a receiver arbitrarily and tell the sender. Messages may be blocking (synchronous: blocking send waits until the message is received; blocking receive waits until a message is available) or non-blocking (asynchronous: the sender continues; the receiver gets a valid message or null). If both send and receive block, it is a rendezvous: the first task to arrive sleeps until the other arrives, they exchange data directly, then both continue.
Comparison: shared memory uses common memory with read/write, is usually faster for local bulk data and needs explicit synchronization, mainly on one machine; message passing uses send/receive, gives simpler isolation, the communication operations can provide synchronization, and it works locally or across machines.

## Producer–consumer and the bounded buffer (slides 16–21)
Examples: a web server produces HTML pages consumed by a client; a compiler produces assembly code consumed by the assembler, whose object modules are consumed by the loader. With shared memory a buffer of items lives in a region shared by producer and consumer; the producer fills it and the consumer empties it, and they must be synchronized so the consumer does not consume what has not been produced. Bounded-buffer code with in and out indices: the producer waits while ((in + 1) % BUFFER_SIZE) == out, writes buffer[in] and advances in; the consumer waits while in == out, reads buffer[out] and advances out. This version can use only BUFFER_SIZE − 1 slots. To use all slots, keep an integer counter of full slots, initially 0: the producer waits while counter == BUFFER_SIZE and does counter++ after adding; the consumer waits while counter == 0 and does counter-- after removing. With message passing the producer simply calls send(next_produced) and the consumer receive(next_consumed).

## Race condition (slides 22–25)
A race condition is a situation where two or more processes or threads access shared data concurrently, at least one modifies it, and the result depends on the order in which their operations run (who reaches certain operations first: hence "race"). Example: counter = 5 and two processes each do counter++ (read, increment a local copy, write). If A reads 5, B reads 5, both compute 6 and both write 6, the final value is 6 (wrong); if A finishes before B starts it is 7 (right). At machine level counter++ is register1 = counter; register1 = register1 + 1; counter = register1, and counter-- is the same with register2. The interleaving S0 producer register1 = counter (5), S1 register1 + 1 (6), S2 consumer register2 = counter (5), S3 register2 − 1 (4), S4 producer counter = register1 (6), S5 consumer counter = register2 (4) leaves counter = 4 instead of 5. Another example: two processes creating children at the same time could both read next_available_pid and assign the same pid to two processes. The part of the program that accesses the shared data must be identified and protected: the critical section.

## The critical-section problem (slides 26–28)
The critical section is the part of a program that accesses shared data or resources and must be protected. With n processes, each has a critical-section segment; when one process is in its critical section no other may be in its own. Each process asks permission in an entry section, then runs the critical section, an exit section and the remainder section. A correct solution must satisfy: 1. Mutual exclusion: only one process executes in the critical section at a time. 2. Progress: if nobody is inside and some processes want to enter, the choice of who enters next cannot be postponed forever (and only processes that want to enter take part). 3. Bounded waiting: there is a bound on how many times other processes may enter after a process has asked and before it is allowed in, so it is not overtaken forever.
Kinds of solutions: software-based (Peterson's solution for two processes; the Bakery algorithm for N > 2 processes); hardware-based (synchronization hardware: atomic instructions). Semaphores and monitors are operating-system-level synchronization primitives; locks are often implemented at application level.

## Interrupt disabling and locks (slides 29–31)
Solution 1, interrupt disable: a process disables all hardware interrupts before entering its critical section and enables them on exit, so nothing else can run meanwhile. Not suitable for multiprocessors: disabling interrupts on one CPU does not stop the others. Solution 2, locks: a lock lets only one process access a shared resource at a time; a process must acquire the lock first, and if another process holds it the requester is blocked until it is released. Software-based locks use flags, turn variables or tickets: Peterson's algorithm (two processes), Dekker's algorithm (more complex, two processes) and the Bakery algorithm (more than two processes, token based). Hardware-based locks use atomic instructions.

## Peterson's solution (slides 32–39)
A two-process mutual-exclusion algorithm for P0 and P1 using two shared variables: flag[2] ("do I want to enter?", the interest) and turn ("if both want to enter, whom should I allow?", the tie-breaker). Idea: declare your interest, give priority to the other process, and wait only if the other process is interested and currently has priority. Code for Pi (j is the other process): while (true) { flag[i] = true; turn = j; while (flag[j] && turn == j); /* critical section */ flag[i] = false; /* remainder section */ }. So P0 sets flag[0] = true; turn = 1; and waits while (flag[1] && turn == 1); P1 sets flag[1] = true; turn = 0; and waits while (flag[0] && turn == 0).
Cases: if only P0 wants to enter, flag[1] is false, so false && true = false and P0 enters at once (same for P1 alone). If both want to enter, both set their flags and both write turn; the last write wins. If P1 writes last (turn = 0), P0 checks flag[1] && turn == 1, which is true && false, so P0 enters; P1 checks flag[0] && turn == 0, which is true, so P1 waits until P0 sets flag[0] = false on exit.
Correctness: mutual exclusion (Pi enters only if flag[j] = false or turn = i; turn breaks a simultaneous tie); progress (an uninterested process has flag = false and cannot block the other; if both are interested turn decides); bounded waiting (a competing process gives the other priority when it asks again, so nobody is overtaken forever). Caveat: Peterson's solution is not guaranteed to work on modern architectures, because processors and compilers may reorder independent memory operations; it is correct only under the classical assumptions of atomic reads/writes and proper memory ordering, so the plain-variable code is not production synchronization code. Understanding why it fails helps understand race conditions.

## Bakery algorithm (slides 40–45)
Mutual exclusion for N > 2 processes, one of the most famous solutions. Idea: when a process wants the critical section it takes a ticket number; the smallest ticket enters first; if two processes get the same ticket, the lower process id goes first (lexicographic order on (ticket, id)). Analogy: customers at a bakery take tokens and the smallest token is served at the single counter (customer = process, token = number, counter = critical section). Four stages: take a ticket; wait for processes that are still choosing tickets; compare ticket numbers; enter, then release the ticket.
Shared data: int number[n] (ticket of Pi; 0 means Pi is not interested) and boolean choosing[n] (true while Pi is choosing its ticket, so nobody compares against a half-chosen ticket). Code for Pi: do { choosing[i] = true; number[i] = max(number[0], …, number[n−1]) + 1; choosing[i] = false; for (j = 0; j < n; j++) { while (choosing[j]); while (number[j] != 0 && (number[j], j) < (number[i], i)); } /* critical section */ number[i] = 0; /* remainder section */ } while (true);
Trace: tickets P0 → 2, P1 → 5, P2 → 0, P3 → 3. P2 wants to enter: number[2] = max(2, 5, 0, 3) + 1 = 6. If P3 is still choosing, P2 waits until choosing[3] = false. P2 then waits until (P0, 2), (P3, 3) and (P1, 5) have entered and left: order P0, P3, P1, P2. With equal tickets, e.g. (P5, 2) and (P0, 2), P0 enters first. Example numbers 4, 2, 7, 3 for P0–P3 give the order P1 → P3 → P0 → P2.
Properties: mutual exclusion (ordering by (ticket, id) is total, e.g. P0 (3,0) enters while P1 (3,1) and P2 (5,2) wait), progress (uninterested processes have number = 0 and block nobody), bounded waiting (later arrivals take larger tickets and cannot keep overtaking). Advantages: fairness, simple idea, no deadlock, no starvation. Disadvantages: not scalable, high time complexity as n grows, busy waiting (a waiting process keeps checking a condition in a loop instead of sleeping, wasting CPU and power), memory overhead for the arrays.

## Synchronization hardware: atomic instructions and spinlocks (slides 46–49)
Peterson and Bakery show that mutual exclusion is possible with shared variables, but real systems need low-level operations supported by the processor. An atomic instruction is indivisible: read–modify–write happens as one step, and once it starts nothing else (another process, an interrupt) can interfere. A spinlock uses busy waiting: the process keeps checking the lock variable until it becomes free; it is usually built from Test-and-Set or Compare-and-Swap. Instructions: Test-and-Set (tests a lock variable and sets it if free), Compare-and-Swap (compares a variable with an expected value and swaps in a new value if they match), Fetch-and-Add (fetches the value and adds to it atomically).

## Test-and-Set and Compare-and-Swap (slides 50–54)
test_and_set(boolean *target) { boolean rv = *target; *target = true; return rv; } runs atomically: "tell me the old lock value and set the lock to busy". Lock usage with boolean lock = false: do { while (test_and_set(&lock)); /* critical section */ lock = false; /* remainder */ } while (true). P0 calls test_and_set, gets false, enters, and lock is now true; P1 calls it repeatedly and keeps getting true (busy waiting / spinning); when P0 sets lock = false, P1's next call returns false and it enters. Properties: mutual exclusion and progress yes, but bounded waiting is not guaranteed: with several competitors there is no queue, so a process can keep losing the race and starve.
compare_and_swap(int *value, int expected, int new_value) { int old = *value; if (*value == expected) *value = new_value; return old; } runs atomically: "change the value only if it is still what I expect". Lock: while (compare_and_swap(&lock, 0, 1) != 0); /* critical section */ lock = 0;. P0 gets 0 back and sets lock to 1; P1 gets 1 back, lock unchanged, and retries until P0 sets lock = 0.
Comparison: Test-and-Set sets the target to a fixed lock value and returns the old value, is very simple and the common teaching example; Compare-and-Swap changes the value only when it matches the expected value, is more flexible and is the basis of lock-free algorithms. Both are atomic and both can build spinlocks.

## Semaphores as defined in the Module 4 notes (slides 55–60)
A semaphore is a synchronization primitive with an integer state, accessed (apart from initialization) only through two atomic operations, wait() and signal(), used to control access to shared resources and to coordinate processes. Proposed by Edsger Dijkstra. wait() is P (Dutch proberen, "to test"); signal() is V (verhogen, "to increment"). They give higher-level synchronization than spinning on test_and_set: a process that cannot enter blocks or sleeps, the CPU does other work, and the finishing process signals a waiter.
Definition in these notes (busy-waiting form): P(Semaphore S) { while (S <= 0) ; /* no operation */ S--; /* enters critical section */ } and V(Semaphore S) { S++; /* leaves critical section */ }. In this definition the semaphore is a non-negative variable shared between threads: S = 1 means nobody is in the critical section, S = 0 means some process is using it, and a process that finds S <= 0 keeps looping until S becomes positive. All changes to the value inside wait() and signal() must be atomic. Mutex usage: semaphore mutex = 1; wait(mutex); /* critical section */ signal(mutex);
Binary semaphore: value only 0 or 1, one shared resource, also called a mutex lock. Trace with S = 1: P0 calls P(1): while (1 <= 0) is false, S-- makes S = 0, P0 enters; P1 calls P(0): while (0 <= 0) is true, so it waits until P0 signals; P0 leaves with V: S = 1; now P1's P(1) passes, S = 0, P1 enters. Counting semaphore: value 0 to N, controls N instances of a resource. Trace with S = 2 and P0, P1, P2: P0 takes instance 1 (S = 1), P1 takes instance 2 (S = 0), P2 waits in while (0 <= 0); when P0 leaves V makes S = 1 and P2 passes (S = 0).
Note on the other definition: OSTEP and the Theory "Semaphore" slides use the blocking version, where wait decrements first and blocks the caller if the value becomes negative, so −k means k waiting threads. Both definitions block the same processes at the same moments; only the number differs (the busy-waiting value never goes below 0).

## Monitors (slides 61–63)
With semaphores each process is responsible for calling wait() and signal() correctly; one badly written process breaks everything, so semaphores are powerful but easy to misuse. A monitor is a higher-level, more structured construct where the monitor itself provides mutual exclusion. A monitor type has programmer-defined operations, local variables that define its state and the procedure bodies; procedures can access only the monitor's local variables and their parameters, and only one process at a time can be active inside the monitor. Condition variables (condition x, y;) allow only x.wait() (the caller is suspended until the condition is signalled) and x.signal() (resumes exactly one suspended process waiting on x, if any). Schematic: shared data, operations (procedures), an entry queue of processes waiting to enter, and one queue per condition variable (x queue, y queue).

## Classical problems: bounded buffer with semaphores (slides 64–68)
Classical problems used to test new synchronization schemes: bounded buffer, readers–writers, dining philosophers. Bounded buffer (producer–consumer): a buffer of n slots; the producer must not insert into a full buffer, the consumer must not remove from an empty buffer, and they must not insert and remove simultaneously. Three semaphores: mutex = 1 (binary, exclusive access to the buffer), empty = n (counting, empty slots), full = 0 (counting, filled slots). Producer: do { wait(empty); wait(mutex); /* add data to buffer */ signal(mutex); signal(full); } while (TRUE); Consumer: do { wait(full); wait(mutex); /* remove data from buffer */ signal(mutex); signal(empty); } while (TRUE). The consumer cannot disturb the buffer until the producer releases the lock.

## Readers–writers problem (slides 69–71 and Theory notes)
A database is shared by readers (only read) and writers (read and write). Several readers may read at the same time without harm, but a writer needs exclusive access: a writer together with any other reader or writer may cause inconsistency. Solution with two semaphores and a counter: readcount = 0 (number of active readers), mutex = 1 (protects readcount), wrt = 1 (shared by readers and writers; gives writers exclusive access). Writer: do { wait(wrt); /* perform the write */ signal(wrt); } while (true). Reader: do { wait(mutex); readcount++; if (readcount == 1) wait(wrt); signal(mutex); /* read */ wait(mutex); readcount--; if (readcount == 0) signal(wrt); signal(mutex); } while (true). The first reader locks writers out and the last reader lets them in; other readers can enter while a reader is inside.
Theory notes version: case 1, two writers, a single semaphore wrmutex = 1 around each write. Case 2, one writer and one reader: semaphores wrmutex = 1 and mutex = 1 and a counter readers = 0, with the same reader protocol as above.

## Dining philosophers (slides 72–78 and Theory notes)
Five philosophers alternate thinking and eating around a table with five chopsticks (forks); a philosopher needs both neighbouring chopsticks to eat: synchronization during resource allocation. Semaphore solution: semaphore chopstick[5], each initialised to 1 (1 = available, 0 = taken). Philosopher i: do { wait(chopstick[i]); wait(chopstick[(i + 1) % 5]); /* eat */ signal(chopstick[i]); signal(chopstick[(i + 1) % 5]); /* think */ } while (TRUE). No two neighbours eat together, but it can deadlock: if all five get hungry at once and each picks up the left chopstick, all chopsticks are 0 and everyone waits forever for the right one (each holds one resource while waiting for another: circular wait).
Deadlock-free monitor solution: a philosopher picks up chopsticks only if both are available. States enum { THINKING, HUNGRY, EATING } state[5]; condition self[5]. Philosopher i may eat only if state[i] == HUNGRY and state[(i + 4) % 5] != EATING (left neighbour) and state[(i + 1) % 5] != EATING (right neighbour). pickup(i): state[i] = HUNGRY; test(i); if (state[i] != EATING) self[i].wait(). putdown(i): state[i] = THINKING; test((i + 4) % 5); test((i + 1) % 5) (check the neighbours). test(i): if the condition holds, state[i] = EATING; self[i].signal(). Initially all THINKING.
Theory notes, four attempts: (1) take right fork then left fork, eat, put both down: deadlock if all take the right fork together. (2) Take the right fork; if the left is available take it and eat, otherwise put the right fork down and sleep(T): no deadlock but possible starvation, even with a random sleep time. (3) Wrap the whole take–eat–put sequence in lock(mutex)/unlock(mutex): correct but only one philosopher eats at a time. (4) Semaphores with states: take_forks(i) locks mutex, sets state[i] = HUNGRY, test(i), unlocks, then down(s[i]); put_forks(i) locks mutex, sets THINKING, tests LEFT and RIGHT, unlocks; test(i) sets EATING and does up(s[i]) if i is hungry and neither neighbour is eating.

## IPC in UNIX (slides 79–83 and Theory IPC.pdf)
Unix/Linux IPC mechanisms: pipes and FIFOs (an anonymous pipe(fd) gives one-way data flow between related processes such as parent and child: write(fd[1], …) to the write end, read(fd[0], …) from the read end; a FIFO is a named pipe in the file system usable by unrelated processes); message queues (discrete messages kept by the kernel, asynchronous); shared memory (a common segment mapped into several address spaces; fastest because there is no kernel copying, but needs semaphores; mmap() maps files or shared-memory objects); semaphores (integer synchronization primitives); signals (lightweight asynchronous event notifications such as SIGINT interrupt, SIGTERM termination request, SIGKILL forced termination, SIGCHLD child status change; not for bulk data); sockets (bidirectional, local Unix-domain or network). The IPC.pdf lab example: a server creates a shared-memory segment with shmget(key 5678, size 27, IPC_CREAT | 0666), attaches it with shmat(), writes the letters a–y and waits until the first byte becomes '*'; the client attaches with the same key, prints the data and writes '*'.

## Multiprocessor locking, lock-free coordination and OS examples (slides 84–91)
On multicore systems many threads may compete for the same lock (lock contention); only one wins and the rest spin or wait. Repeated atomic updates of the same lock cause cache-coherence traffic (cache-line bouncing): a lock can be correct yet slow. Scalable locks reduce contention: the ticket lock (take a token at a counter), queue-based locks where threads wait in a queue, the MCS lock (each waiting thread spins on its own queue node) and the CLH lock (a thread waits on its predecessor's state). Lock-free coordination uses atomic operations such as CAS instead of lock ownership, avoiding blocking, contention and deadlock in multi-lock designs.
Examples: Solaris uses adaptive mutexes (spin if the holder is running on another CPU, otherwise sleep), condition variables, readers–writers locks for longer sections, and turnstiles with priority inheritance. Windows XP masks interrupts on uniprocessors, uses spinlocks on multiprocessors (a spinlocking thread is never preempted) and dispatcher objects (mutexes, semaphores, events like condition variables, timers) in signalled or non-signalled state. Linux before 2.6 disabled interrupts for short critical sections; 2.6 and later is fully preemptive and provides semaphores, spinlocks and reader–writer versions of both (on a single CPU spinlocks become enabling/disabling kernel preemption). Pthreads (OS-independent) provides mutex locks and condition variables, with non-portable read–write locks and spinlocks.

## Theory slides: semaphores in the blocking style
These slides define a semaphore as a variable with an underlying counter and two functions: up/post increments the counter; down/wait decrements it and blocks the calling thread if the resulting value is negative. A semaphore with initial value 1 is a simple lock (binary semaphore = mutex). Semaphores can also order threads, like condition variables: e.g. a parent waiting for its child uses a semaphore initialised to 0. Producer/consumer needs two semaphores for signalling (one tracking empty slots so the producer waits when there are none, one tracking full slots so the consumer waits when there are none) and one semaphore as a mutex for the buffer. Incorrect solution: if the mutex is acquired before waiting on the empty/full semaphore, a waiting thread sleeps holding the mutex and the signalling thread can never wake it: deadlock.

## Theory slides: locks, spinlocks and sleeping mutexes
A lock protects a critical section: all threads share the lock, one succeeds and becomes the owner, the others cannot proceed until the owner releases it (pthreads provides such locks). Goals of a lock: mutual exclusion, fairness (no starvation) and low overhead. Disabling interrupts is not enough in general: it is privileged and can be misused, and it does not work on multiprocessors; it is used only inside the OS on single-processor systems. A lock built from a plain flag fails: a thread may be interrupted after its spin ends but before it sets the flag, so the race just moves into the lock code. Hardware atomic instructions fix this: test-and-set builds a spinlock (spin until acquired), and compare-and-swap can too. Alternative: a sleeping mutex, where a contending thread gives up the CPU (yield() moves it from running to ready) instead of spinning. Most user-space locks are sleeping mutexes; locks inside the OS are spinlocks, and while holding one the OS must disable interrupts on that core (an interrupt handler could ask for the same lock and spin forever) and must never block.

## Theory slides: condition variables
Locks give mutual exclusion; another common need is waiting and signalling (thread T1 continues only after T2 has finished a task). Busy-waiting on a variable works but wastes CPU, so condition variables are used: a CV is a queue a thread puts itself in while waiting for a condition; another thread that makes the condition true signals the CV (signal wakes one thread, broadcast wakes all). Example: a parent waiting for its child checks a done flag in a while loop before waiting (the child may already have finished, and some implementations wake threads spuriously). The lock must be held when calling wait and signal, otherwise a wakeup can be missed (the parent sees done = 0, is interrupted, the child sets done and signals with nobody waiting, then the parent sleeps forever); wait releases the lock before sleeping. Producer/consumer with two CVs: e.g. in a multithreaded web server one thread puts requests in a bounded shared queue and worker threads take them out.

## Theory slides: concurrency bugs and threads
Concurrency bugs are non-deterministic and depend on the execution order. Non-deadlock bugs: atomicity bugs (an atomicity assumption is violated, e.g. one thread reads and prints a shared item while another modifies it; fix with locks, even for reads) and order-violation bugs (thread 1 assumes thread 2 has already run; fix with condition variables or semaphores). Deadlock bugs are covered in the deadlock notes.
Threads: a thread is like another copy of a process that executes independently but shares the same address space (code, heap); each thread has its own program counter and its own stack. Processes created with fork share no memory and need IPC; threads share globals, so communication is easier and the memory footprint smaller. Concurrency = running several threads at the same time even on one core by interleaving; parallelism = running them on different cores at once. The OS schedules kernel threads independently, saving their context in a thread control block (TCB); every PCB has one or more TCBs; Linux pthreads are kernel threads. Two threads each incrementing a shared counter 10^7 times without a lock often end below 2 × 10^7, because counter = counter + 1 is several machine instructions: a race condition on a critical section, fixed by mutual exclusion (locks).
